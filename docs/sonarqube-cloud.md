# SonarQube Cloud setup

[Português](sonarqube-cloud.pt-BR.md) | **English**

This repository includes an optional SonarQube Cloud workflow at `.github/workflows/sonar.yml`. The integration is designed for .NET libraries generated from this template and remains disabled until `SONAR_TOKEN` is configured.

## What the workflow does

When enabled, the workflow runs on pull requests targeting `main` and on pushes to `main`.

It:

- restores the locally pinned SonarScanner for .NET;
- restores NuGet dependencies in locked mode;
- performs a non-incremental Release build under Sonar analysis;
- runs the test suite and produces OpenCover coverage for Sonar;
- excludes `scripts/**` from Sonar analysis;
- waits for the Sonar Quality Gate and fails the workflow when the gate fails;
- reports a `sonar.projectVersion` that follows the latest reachable release tag;
- falls back to the project's `PackageVersion` before the first release tag exists.

The primary CI workflow remains responsible for the repository's normal build, warnings-as-errors policy, package validation, and CI artifacts. SonarQube Cloud complements that baseline instead of replacing it.

## 1. Create or import the SonarQube Cloud project

Create the project in SonarQube Cloud and bind it to the GitHub repository that will run the analysis.

For a normal GitHub import, the default coordinates used by this workflow are:

```text
project key  = <github-owner>_<repository-name>
organization = <github-owner>
host         = https://sonarcloud.io
```

If your SonarQube Cloud project uses those values, only `SONAR_TOKEN` is required.

## 2. Disable Automatic Analysis

When this GitHub Actions workflow is used, keep SonarQube Cloud **Automatic Analysis disabled** for the project.

The CI-based scanner is responsible for the analysis and coverage import. Running both approaches can produce duplicate or conflicting analyses, and Automatic Analysis does not replace the coverage generated by the .NET test workflow.

## 3. Configure the GitHub secret

In the target GitHub repository, open:

```text
Settings
→ Secrets and variables
→ Actions
→ Secrets
→ New repository secret
```

Create:

```text
Name: SONAR_TOKEN
Value: <token authorized to analyze the SonarQube Cloud project>
```

Never commit the token to the repository.

If `SONAR_TOKEN` is absent or empty, the Sonar workflow intentionally exits successfully without starting an analysis.

## 4. Configure repository variables when needed

The workflow has safe defaults for the normal GitHub/SonarQube Cloud naming convention. Override them only when your project uses different coordinates.

Under:

```text
Settings
→ Secrets and variables
→ Actions
→ Variables
```

configure any required values:

```text
SONAR_PROJECT_KEY
SONAR_ORGANIZATION
SONAR_HOST_URL
```

Typical values are:

```text
SONAR_PROJECT_KEY=<organization>_<repository>
SONAR_ORGANIZATION=<sonar-organization-key>
SONAR_HOST_URL=https://sonarcloud.io
```

These are Repository Variables, not secrets. `SONAR_TOKEN` remains the only credential.

## 5. Configure New Code

The workflow explicitly sends `sonar.projectVersion`.

Its version resolution is:

1. find the newest reachable Git tag matching `v*.*.*`, using semantic version ordering;
2. remove the leading `v` and use that release as `sonar.projectVersion`;
3. before the first release tag exists, use the MSBuild `PackageVersion` as a fallback.

Example:

```text
latest reachable tag: v1.4.0
sonar.projectVersion: 1.4.0
```

This makes SonarQube Cloud's **Previous Version** New Code strategy usable with the repository's release model. After a release tag is created, the next analysis on `main` sees the new tag and advances the version baseline.

If the project intentionally uses another New Code strategy, keep the workflow version reporting in place unless there is a documented reason to remove it.

## 6. Configure the Quality Gate

The workflow uses:

```text
sonar.qualitygate.wait=true
sonar.qualitygate.timeout=300
```

Therefore a failed Quality Gate fails the Sonar GitHub Actions job on both pull requests and pushes to `main`.

The built-in **Sonar way** gate is a reasonable starting point. A custom gate can be used when the project has an explicit quality policy, but do not weaken thresholds merely to make CI green.

For a small deterministic library, coverage targets can be stricter than for a typical application, but exclusions should represent genuinely non-product code rather than metric manipulation.

## 7. Coverage behavior

Tests are executed with Coverlet MTP using OpenCover output:

```text
--coverlet
--coverlet-output-format opencover
```

The scanner imports the report through:

```text
sonar.cs.opencover.reportsPaths=**/coverage.opencover*.xml
```

This is independent from the Cobertura coverage artifact produced by the main CI workflow.

Production code should not be excluded from coverage solely to increase the reported percentage.

## 8. Analysis exclusions

The baseline intentionally excludes:

```text
scripts/**
```

through:

```text
sonar.exclusions=scripts/**
```

The repository's helper and release scripts remain validated by their own CI/release flows but are not part of the Sonar project analysis baseline.

Add more exclusions only when files are demonstrably outside the product analysis scope. Avoid broad exclusions such as `src/**`, validators, or domain code.

## 9. Git history requirement

The Sonar checkout uses:

```yaml
fetch-depth: 0
```

Do not replace it with a shallow checkout unless the version-resolution strategy is also redesigned. Full history is required so the workflow can discover reachable release tags reliably and so Sonar can use complete SCM information.

## 10. Recommended GitHub branch protection

After the integration is stable, include the Sonar job among the required checks for `main` when your repository governance requires it.

The current job name is:

```text
Analisar com SonarQube Cloud
```

Verify the exact emitted check name on a recent pull request before adding it to a ruleset.

## Generated repositories

GitHub repository secrets, variables, SonarQube Cloud projects, quality gates, and branch-protection settings are not copied by `dotnet new` or GitHub Template Repository creation.

Every generated repository must configure its own Sonar project and `SONAR_TOKEN`. Repository variables are only needed when the default coordinates do not match the Sonar project.

## Troubleshooting

### The workflow says SonarQube Cloud is disabled

Confirm `SONAR_TOKEN` exists under **Settings → Secrets and variables → Actions → Secrets** and is available to the workflow event.

### `SONAR_PROJECT_KEY` or organization cannot be resolved

Check the Sonar project coordinates and, when they differ from the GitHub-derived defaults, configure `SONAR_PROJECT_KEY` and `SONAR_ORGANIZATION` as Repository Variables.

### Analysis succeeds but the workflow fails at the final scanner step

If the log contains:

```text
QUALITY GATE STATUS: FAILED
```

the integration itself succeeded. Open the SonarQube Cloud project and inspect the failed Quality Gate conditions. Fix the underlying quality problem or deliberately adjust the project's gate policy; do not disable `sonar.qualitygate.wait` merely to hide the failure.

### Coverage is missing

Confirm the test step generated an OpenCover file and look for the Sonar log entry that parses `coverage.opencover*.xml`. Do not change the Sonar property to Cobertura while the workflow is generating OpenCover for this analysis.

### Project version never advances

Confirm releases create Git tags matching:

```text
v*.*.*
```

and that the tags are reachable from `main`. Keep `fetch-depth: 0` on the checkout.

## Security notes

- keep `SONAR_TOKEN` only in GitHub Secrets;
- do not print token values in workflow diagnostics;
- prefer repository variables for non-secret coordinates;
- do not add long-lived credentials to source files;
- keep the workflow's repository permissions read-only unless a future Sonar feature has a documented need for additional access.
